# 현재 구현: 12단계 — 탈환 작전실을 완성합니다

## 12단계 저장점

커밋 제목은 「12단계 저장점」입니다. 검사한 12단계 구현과 아래 재현 안내를 함께 보존합니다. `aleph.config.json`의 단계 12, 기존 운영 주소·로그인 발급자·원본 API·복구 경로 및 작전실 허용 경로를 구현과 대조했으며 `judgeIssuer`는 변경하지 않았습니다. 학생 판정기·탐지 규칙도 그대로입니다. 다시 확인할 명령은 `node --test test/operations-summary.test.mjs test/note-restore.test.mjs`이며, 승인된 관리자 화면에서 **탈환 작전실 → 서버 요약 새로고침**을 누릅니다. 정상 요청의 요약과 가린 기록은 일치해야 하고 무로그인·미승인·권한 없는 요청은 거부되어야 합니다.

저장점 커밋 뒤 `npm run bundle`로 해당 커밋의 제출 JSON을 별도 생성합니다. 생성 파일은 Git에 넣지 않습니다. 묶음 생성 성공·배포 커밋 일치·HTTP 점검 통과·공식 심판 통과는 각각 별도로 확인하며, 이 README는 실행하지 않은 배포·DB 설정·실제 엔진 회수를 완료로 기록하지 않습니다.

## 설치부터 실행까지 재현 순서

1. **코드를 고정합니다.** Git과 Node.js 22 이상을 준비합니다. 기존 작업 폴더를 덮어쓰지 않고 새 폴더에 복제합니다. 다음 명령은 재현용 안내이며 이번 문서 작업에서 새 복제·설치는 실행하지 않았습니다.

   ```powershell
   git clone https://github.com/jaehyun7849/aleph-defense-starter.git aleph-stage12-reproduce
   cd aleph-stage12-reproduce
   git switch --detach 5920cf93d4983fa4d627c7dfa653c93be6fb9535
   git log -1 --format="%H %s"
   git status --short
   npm ci
   ```

   커밋 번호가 위 기준과 같고 작업 상태가 깨끗해야 합니다. 의존성은 `package-lock.json`으로 고정합니다. 이후 기능을 변경할 때는 별도 작업 브랜치를 만듭니다.

2. **학생 규칙을 로컬에서 검사합니다.** 저장소 루트에서 차례로 실행합니다. 시험은 끝나면 자동 종료되며 상주 판정기/탐지 서버를 시작하지 않습니다.

   ```powershell
   npm run decider:test
   npm run detect:test
   node --test test/operations-summary.test.mjs test/note-restore.test.mjs
   node --test test/*.test.mjs
   npm run build -- --local
   ```

   정상 등록·허용 자원 요청은 `allow`, 미등록은 `deny`, 계약의 복합 이상은 `step_up`이어야 합니다. 탐지는 정상 사건에서 `observe`, 제공 v1의 동일 주체 10분 내 GET 121건 이상에서 `propose_revocation`이어야 합니다. 복구는 지정 B의 검증된 한 건만 성공하고 잘못된 소유자·사본·해시는 쓰기 전에 거부되어야 합니다. 실패·미실행은 그대로 기록합니다. 정적 로컬 빌드는 `/api/*`를 실행하지 않으며, 이 프로젝트에는 `npm start`/`npm run dev` 스크립트가 없습니다.

3. **서버를 준비합니다.** 기존 자료실의 Supabase 프로젝트·인증 계정·notes 테이블을 보존합니다. 신규 설치라면 이 저장소만으로 기존 운영 DB와 계정이 자동 생성되지 않으므로 수업의 초기 자료실 설정이 먼저 필요합니다. Supabase SQL Editor에서 [DEMO_APPROVAL.sql](docs/DEMO_APPROVAL.sql), [OPERATIONS_AUDIT.sql](docs/OPERATIONS_AUDIT.sql)을 적용합니다. 이미 적용한 데모 테이블은 재생성하지 않습니다. 원본 DB의 브라우저 역할 직접 CRUD 차단을 유지합니다.

   Vercel 프로젝트의 환경변수 비밀 입력란에 기존 `SUPABASE_URL`, `SUPABASE_SECRET_KEY`, `DEMO_APPROVAL_ADMIN_IDS`를 설정합니다. 자원·강사 매핑이 필요하면 [RESOURCE_SCOPES](docs/RESOURCE_SCOPES.md)의 `VAULT_RESOURCE_POLICY`를 설정합니다. 지정 복구를 사용할 때만 [NOTE_RESTORE](docs/NOTE_RESTORE.md)의 서버 전용 복구 설정을 준비합니다. 문서에는 변수 이름만 적으며 값·계정 UID·사본 원문을 복사하지 않습니다.

4. **자료실을 배포합니다.** 위 커밋을 Vercel 배포 대상으로 선택하고 빌드 명령 `npm run build`, 출력 폴더 `public`을 사용합니다 (`vercel.json`). 배포의 `/aleph.json`에서 `commit`과 단계 12를 대조합니다. 커밋이 다르면 해당 배포를 이 기준의 실행으로 기록하지 않습니다. 운영 주소는 [자료실](https://choi-bujang-secret-vault-2-pi.vercel.app/)이며, 주소가 같아도 실제 배포 커밋은 별도로 확인해야 합니다. Vercel 인증 보호가 반환한 401과 자료실 API의 로그인 거부는 구분합니다.

5. **기존 앱에서 실행합니다.** 자료실 첫 화면에서 로그인 → **기기 승인 요청**을 누릅니다. 별도 창의 `/demo-approval.html`에서 관리자 로그인 → **관리자 승인 목록 확인** → 해당 요청의 **관리자 승인**을 누릅니다. 원래 화면의 **승인 결과 확인** 뒤 본인 자료 CRUD가 열려야 합니다. 다른 사람의 메모와 권한 없는 공지 수정은 계속 거부되어야 합니다. 자세한 순서는 [DEMO_APPROVAL](docs/DEMO_APPROVAL.md)을 따릅니다.

   앱 설치는 지원 브라우저 메뉴의 **앱 설치 / 홈 화면에 추가**로 선택합니다. 설치 전후 승인 규칙은 같습니다. 오프라인에서는 연결 안내만 제공하며 자료 조회·변경은 허용하지 않습니다. 설치 표시·로그인·승인 요청 버튼 클릭만으로 자료가 열리면 실패입니다.

6. **작전실 수치를 대조합니다.** 관리자 계정의 현재 페이지가 승인된 뒤 **탈환 작전실 → 서버 요약 새로고침**을 누르고 **수치 대조용 가린 서버 기록**을 펼칩니다. 같은 응답의 최근 최대 100건과 수치·복구 버전을 비교합니다. 규칙 목록은 구현 목록이며 실제 판정 횟수가 아닙니다. 미연결 탐지·실제 회수·정책 복구는 미실행, 기록 조회 실패는 확인 불가로 남아야 합니다. 메모 본문·제목·소유자·토큰은 표시하지 않습니다. [OPERATIONS_ROOM](docs/OPERATIONS_ROOM.md)에 집계 범위와 저장 실패의 한계를 적었습니다.

## 중지와 다시 접속

- **로컬 명령:** 시험·빌드는 자동 종료됩니다. 실행 중 중단은 해당 터미널에서 `Ctrl+C`를 누릅니다. 학생 판정기·탐지 규칙에 별도의 데몬 중지 명령은 없습니다.
- **현재 앱 사용 종료:** 자료실의 **로그아웃**을 누르고 설치 앱/탭을 닫습니다. 화면의 자료와 작전실 기록이 지워져야 합니다. 로그인과 데모 핸들은 페이지 메모리에만 있으므로 새로고침·새 탭도 새 로그인과 승인이 필요합니다.
- **서버에서 데모 접속 취소:** 별도 관리자 화면에서 해당 요청의 **승인 취소**를 누릅니다. 원래 화면의 다음 상태 확인·자료 요청은 거부되어야 합니다. 기존 화면은 서버 상태를 다시 확인할 때 잠기므로, 즉시 모든 탭에서 본문이 사라지는 푸시 회수라고 주장하지 않습니다. 실제 ALEPH SDP 기기 회수와는 별개입니다.
- **운영 서비스 전체 중지:** 로그아웃이나 PWA 종료는 Vercel 배포를 중지하지 않습니다. 운영 담당자가 Vercel 공식 프로젝트 설정에서 접근·배포를 통제해야 합니다. 이 저장소에는 서비스 전체 종료 CLI와 ALEPH SDP 엔진 중지 도구가 없습니다. DB·감사 기록 삭제를 중지 수단으로 사용하지 않습니다. 로그아웃 후에도 이미 발급된 접근 토큰은 만료까지 유효할 수 있습니다.

## 복구와 복구 후 재검증

정책과 메모 복구는 별개입니다. 침해 전에 검토한 사본·별도 보관 해시·버전이 없으면 복구를 실행하지 않고 미실행으로 남깁니다. 현재 코드를 사본으로 만들어 자동으로 안전하다고 지정하지 않습니다.

1. **격리 정책 복구:** [POLICY_PREVIEW](docs/POLICY_PREVIEW.md), [POLICY_RESTORE](docs/POLICY_RESTORE.md)에 따라 운영 저장소 밖의 시험 폴더를 준비합니다. 다음 자리표시자는 실제 사전 검토 기록으로 바꿉니다.

   ```powershell
   npm run policy:preview -- --backup <검증한사본.json> --sha256 <사전64자리해시> --version <안전40자리커밋> --trial-dir <격리시험폴더>
   npm run policy:restore -- --backup <검증한사본.json> --sha256 <사전64자리해시> --version <안전40자리커밋> --trial-dir <격리시험폴더>
   ```

   두 번째 명령도 확인값 없이 실행하면 계획만 보여 줍니다. 대상·변경·보존 목록을 검토한 뒤 같은 명령에 `--confirm <출력된planSha256>`을 붙여야 적용합니다. 복구 범위는 시험 폴더의 `src/engine-resource-grants.mjs` 한 개입니다. 다른 파일·기존 감사 기록·운영 배포·DB는 되돌리지 않습니다. 실제 운영 정책 복구는 제공 엔진 운영 절차가 필요하며 여기서는 미연결입니다.

2. **지정 메모 복구:** 서버의 비공개 검토 사본과 독립 해시, 등록한 시험 B 계정, 현재 페이지의 데모 승인을 준비합니다. 기존 인증·승인 헤더를 사용하는 클라이언트에서 `POST /api/restore-note`에 `{id, ownerId, contentSha256}`만 전달합니다. 본문 내용은 서버 사본에서만 읽습니다. 전용 복구 버튼은 없으며 토큰을 콘솔·셸 명령·스크린샷에 복사하는 방식은 사용하지 않습니다. 인증된 호출 수단이나 검증 사본이 준비되지 않았으면 미실행입니다.

   성공 응답의 ID·소유자·해시 및 `restored: true`를 사본과 대조하고 같은 계정으로 다시 읽어 내용 해시를 메모리에서 확인합니다. 다른 메모·기존 감사 기록은 보존되어야 합니다. A/무로그인/승인 없음/다른 대상/변조 사본은 거부되어야 합니다. 작전실의 메모 복구 버전은 확인된 사본 해시의 가린 값이며 정책 커밋 버전이 아닙니다. 감사 저장 실패는 `X-Operations-Audit: unavailable`로 구분하고 성공 건수가 완전하다고 주장하지 않습니다.

로그인 뒤 ‘기기 승인 요청’과 ‘승인 결과 확인’ 버튼을 표시합니다. 확인 전에는 메모 목록·추가/수정 화면을 숨기고 목록을 비우며 자료 API를 호출하지 않습니다. 새 서버 상태 확인을 통과한 뒤에만 기존 화면이 열리고, 각각의 자료 요청 전에도 다시 확인합니다. 로그아웃·계정 변경·오프라인·확인 오류는 화면을 잠급니다. 설치 여부와 브라우저 저장값은 승인의 근거가 아닙니다. 기기 키를 생성하거나 저장하지 않습니다.

**현재 실제 승인 연결은 미구현입니다.** 사용자가 제공 엔진의 승인 API 문서/경로가 없다고 확인했습니다. 기존 로그인 검증에는 기기 증명이 없고, DECIDER_REQUEST의 deviceRegistered는 엔진에서 판정기로 전달하는 값이지 브라우저 승인 조회 API가 아닙니다. 로컬 UI 경계 GET/POST /api/device-approval는 로그인 확인만 수행하고 503/device_approval_unavailable를 반환합니다. 실제 승인 요청을 접수하거나 기기 등록·권한을 변경하지 않으며 성공으로 표시하지 않습니다. 따라서 현재 환경에서는 승인 버튼을 눌러도 자료실이 열리지 않습니다.

public/device-approval.js의 aleph.device-approval.v1 형식은 UI 연결을 위한 내부 형식이며 제공 엔진 계약이라고 주장하지 않습니다. 실제 승인을 연결하려면 엔진이 검증한 기기와 현재 로그인·세션을 묶은 상태 조회와 요청 채널, 보호 API에서도 그 증명을 확인하는 계약이 필요합니다. 현재 notes/notices/restore API의 기존 로그인·소유자 권한 검사는 보존합니다. UI 잠금은 API의 실제 기기 검증을 대신하지 않으며 직접 API 경로의 기기 확인은 아직 미연결입니다.

직접 확인: `node --test test/device-approval.test.mjs test/webapp.test.mjs test/auth-handler.test.mjs test/resource-scope.test.mjs test/decider-entry.test.mjs test/decider-input.test.mjs test/decider-step-up.test.mjs test/note-restore.test.mjs`. 로그인 뒤 기기 승인 요청을 누르면 서버 연결 미준비·미접수 결과가 나오고 자료는 없어야 합니다. 모의 서버 등록 확인·대기·오류·로그아웃 이후 지연 응답을 로컬 시험으로 검증합니다. 2026-10-14 관련 로컬 검사 38건과 판정기 가상 요청 9건이 모두 통과했습니다. 실제 엔진이 등록 기기를 확인한 시험이 아니라 명시된 모의 서버 응답을 이용한 화면/요청 시험입니다. 실제 기기 승인 및 승인된 기기의 정상 자료 접근·설치형 앱 실측은 미실행입니다. 별도 프로그램·인증서·CA·서명 키·임의 기기 권한을 만들지 않습니다.

## 10단계 저장점: 시험 계정 B 메모 한 건 복원

자료실 복구 API 서비스의 경로는 **POST /api/restore-note**입니다. 기존 메모 주소와 화면 메뉴는 보존합니다. 서버에 등록한 시험 계정 B만 호출할 수 있고, 서버 비공개 사본의 지정 ID 한 건만 복원합니다. 요청의 id·ownerId·contentSha256과 사본을 대조하고 결과도 같은 세 항목으로 검증합니다. 다른 메모와 감사 테이블을 수정하거나 삭제하지 않습니다. 제출 설정의 restoreRoute는 구현된 경로 문자열 /api/restore-note이며 allowedRoutes의 POST 항목과 일치합니다. 10단계 배포 정보 aleph.json에도 복구 경로를 표시합니다. 공개 실습 저장소의 경로 문자열 사용례를 참고한 등록이며 공식 심판의 요청 본문 계약과 실제 연결 성공은 아직 미확인입니다. 현재 설정 단계는 11입니다.

비공개 환경변수 VAULT_RECOVERY_TEST_B_ID, VAULT_NOTE_BACKUP, VAULT_NOTE_BACKUP_SHA256을 운영자가 공식 서버 설정에 넣어야 합니다. 실제 사본·키·시험 계정 정보를 Git이나 답변에 넣지 않습니다. 사본 미제공·검증 실패는 중단합니다. 해시는 사본 무결성을 검증하며 사본의 안전성은 사전 검토가 필요합니다. [형식과 시험 방법](docs/NOTE_RESTORE.md).

`node --test test/note-restore.test.mjs`는 시험 B의 가상 메모만 복원해 ID·소유자·내용 해시 일치와 다른 메모·감사 보존을 확인합니다. 실제 B 로그인·비공개 사본·운영 DB 복원·공식 심판은 아직 미실행입니다.

## 10단계 복구 뒤 1~9단계 재검증 순서

아래는 앞으로 실제 복구 후 실행할 순서입니다. **실제 안전 사본과 실제 B 계정 자료로 복구한 뒤의 재검증은 현재 모두 미실행**입니다. 기존 가상 파일/모의 SDK 시험의 통과를 이 표의 통과로 옮겨 적지 않습니다. 정책 복원은 격리 시험 폴더의 메모 권한 파일 한 개, 자료 복원은 지정 B 메모 한 건으로 범위를 한정합니다.

1. **안전 사본과 실행 대상 확인.** 사전 검토 기록의 안전 버전·별도 SHA-256을 확인하고 `npm run policy:preview` 및 확인값 없는 `npm run policy:restore`에 실제 사본·시험 폴더 인수를 전달합니다. 사용 형식은 [미리보기](docs/POLICY_PREVIEW.md)와 [시험 복원](docs/POLICY_RESTORE.md)을 따릅니다. 버전·변경 파일·줄 범위·보존 파일·감사 기록을 확인합니다. 사본 누락·해시/버전 불일치·운영 폴더이면 중단합니다.

2. **확인한 시험 정책만 복원.** 표시된 `planSha256`을 확인해 같은 명령에 `--confirm`으로 전달합니다. `applied: true`와 시험 폴더의 메모 권한 파일 해시가 안전 사본과 같은지 확인합니다. 다른 서비스 파일과 기존 감사 기록의 기존 부분이 그대로인지 대조하고 새 복원 감사 항목만 추가됐는지 확인합니다. 새 Node 프로세스를 사용해 이전에 로딩한 정책 캐시를 재사용하지 않습니다. 운영 정책을 되돌렸다고 기록하지 않습니다.

3. **시험 B 자료 한 건 복구·대조.** 비공개 검토 사본이 준비된 환경에서 인증된 시험 B로 `POST /api/restore-note`를 호출합니다. 본문은 등록한 대상의 id·ownerId·contentSha256 세 값만 사용합니다. 성공 응답 세 항목을 사본과 대조하고, B의 기존 `GET /api/notes/:id`로 다시 읽어 같은 ID·사본 소유자·내용 해시인지 확인합니다. 내용 해시는 NOTE_RESTORE.md의 title/body 순서로 메모리에서 계산하며 본문을 출력하거나 기록하지 않습니다. 다른 메모와 기존 감사 기록도 그대로인지 대조합니다. 로그인·서버 설정·사본이 준비되지 않으면 미실행으로 남깁니다.

4. **1~2단계 공개 자료·화면 점검.** 현재 보호된 자료실 화면이 열리고 정상 로그인 화면이 유지되는지 확인합니다. 시크릿 창의 `/data.json`은 메모 0건 또는 404여야 하고 초기 공개 확인 표시가 없어야 합니다. 비로그인 `/api/notes` 및 개별 메모 조회는 401/403 JSON 오류이며 자료가 없어야 합니다. 실제 자료가 보이면 다음 단계로 넘어가지 않습니다.

5. **3~5단계 로그인·최종 API·원본 DB 점검.** 배포된 `/owner-check.html`에서 서로 다른 A/B 시험 계정으로 「임시 메모로 점검 시작」을 누릅니다. 본인 생성·목록·조회·수정·삭제는 성공, 무로그인은 401, 타인 메모 접근은 404, 소유자 변경은 403이어야 합니다. 이 화면은 새 임시 메모를 시험하므로 3번의 복구 대상 한 건 대조를 대신하지 않습니다. 공식 DB 설정에서 기존 anon/authenticated 직접 CRUD 권한 회수가 유지되는지 확인합니다. 화면·공유 모듈에 서버 키가 없어야 하며 DB를 공개해 정상 동작을 맞추지 않습니다. 원본 DB 역할 점검을 하지 않았다면 별도 미실행입니다.

6. **6~8단계 판정기 정상/금지 요청 재검증.** 복원한 시험 폴더의 `src/decider.mjs`를 직접 불러와 아래 명령을 실행합니다. `<복원한 시험 폴더>`에는 실제 격리 폴더를 넣습니다. 현재 자료실 폴더에서 실행하며, 기본 판정기로 대체해 시험하지 않습니다.

```powershell
$env:ALEPH_TRIAL_DIR = '<복원한 시험 폴더>'
@'
import { resolve, join } from 'node:path';
import { pathToFileURL } from 'node:url';

for (const item of results) console.log(`${item.passed ? '통과' : '확인 필요'} · ${item.name}`);

'@ | node --input-type=module

```

정상 등록 기기와 A 자기 메모는 allow, 미등록은 deny/device_not_registered, 복합 이상은 step_up/step_up_required, 유효한 모의 추가 확인 뒤 요청은 allow여야 합니다. ## 6단계 저장점: 등록 기기 판정기 확인

`src/decider.mjs`의 `device_registered` 규칙은 `request.deviceRegistered === true`일 때 `allow`와 `approved`를 반환합니다. 미등록이거나 값이 없으면 `deny`와 `device_not_registered`를 반환합니다. 아래 확인은 로컬 판정기 연습입니다.

1. 저장소 루트에서 터미널을 열고 `npm run decider:test`를 실행합니다. 별도로 설치할 접속 프로그램이나 화면에서 누를 버튼은 없습니다.
2. 출력에 `통과 · 등록 기기의 정상 요청`이 나오는지 확인합니다. 이 검사는 등록 요청의 응답 형식과 `allow` 결정을 확인합니다.
3. 출력에 `통과 · 미등록 기기의 가상 요청`이 나오는지 확인합니다. 이 검사는 미등록 요청의 응답 형식과 `deny`, `device_not_registered`를 함께 확인합니다.

2026-10-13 로컬 실행에서 두 검사 모두 통과했고, 같은 가상 요청을 직접 호출해 다음 응답도 확인했습니다.

```text
통과 · 등록 기기의 정상 요청
통과 · 미등록 기기의 가상 요청
등록 기기의 정상 요청 → allow · approved
미등록 기기의 가상 요청 → deny · device_not_registered
```

미등록 기기 공격은 심판이 맡습니다. 이 로컬 연습 결과는 실제 접속 차단이나 공식 심판 통과 증거가 아닙니다.

## 7단계 저장점: 재확인 계약과 가상 사건 검증

판정기에 `step_up_required` 규칙을 추가했습니다. `judge_fixture` 가상 정보에서 22시~다음 날 6시 전, `unusual` 네트워크, 최근 60초 이내 `risk_signal` 20건 이상이 함께 나타나는 자료실 GET 요청은 `step_up`과 사유 `step_up_required`를 반환합니다. 지역 하나만으로 차단하지 않으며 기존 미등록 기기 거부를 유지합니다. 입력 검사에서 출처 불명·계약 밖 헤더·잘못된 형식은 거부하고, 누락 정보는 정상값으로 채우지 않습니다.

`docs/DECIDER_REQUEST.md`에는 엔진이 전달하는 `stepUp: { verified, authAgeSeconds }`가 있습니다. 그러나 이 폴더에는 문서가 참조하는 `student-kit/sdp-core/decision-contract.mjs` 및 같은 로그인 주체의 재로그인 시각을 검증해 이 값을 생성하는 운영 엔진·릴레이 구현이 없습니다. `api/notes.js`도 판정기를 호출하지 않습니다. 전달 항목의 존재만으로 실제 재인증 연결이 준비됐다고 판단하지 않습니다. 토큰 발급 시각이나 브라우저가 보낸 값을 재로그인 증거로 대신 쓰지 않습니다.

2026-10-13 로컬 가상 요청만 시험했습니다. `node --test test/decider-input.test.mjs test/decider-step-up.test.mjs`의 7개 검사가 통과했습니다. 정상 사건은 `allow`, 복합 사건의 확인 전은 `step_up / step_up_required`, 같은 가명 주체와 새 요청 ID에 모의 `stepUp: { verified: true, authAgeSeconds: 60 }`를 넣은 새 사건은 `allow`였습니다. 이 마지막 결과는 실제 재로그인 실측이 아닙니다.

실제 재로그인 전 자료 차단: **미실행**. 같은 사용자로 새 로그인한 뒤 새 요청의 자료 허용: **미실행**. 운영 엔진의 동일 주체 검증·재로그인 시각 검증·자료 전달 보류·새 요청 재판정 계약과 연결이 확인된 환경에서만 실측합니다. 토큰 원문·비밀번호·자료 본문은 시험 기록에 넣지 않습니다.

이번 저장점은 판정기의 가상 사건 규칙과 실행·기록 안내입니다. 실제 재인증 연결과 자료 전달 전 차단은 구현·실측하지 않았습니다.

사용자가 권한 회수 후 기존 배포에서 추가·수정·삭제와 로그아웃이 동작한다고 보고했습니다. 새 서버 로그인 코드의 실제 A·B 계정 점검은 배포 후 필요합니다. 로컬 모의 시험은 공식 심판 판정이 아닙니다.
11단계 보완 이후 브라우저 세션은 페이지 메모리에만 있습니다. 새로고침·새 탭은 다시 로그인합니다. 비밀번호·기기 키를 저장하지 않으며 메모리의 갱신 토큰으로 요청 전 만료를 처리합니다.
로그아웃은 현재 세션의 갱신 권한을 회수합니다. 이미 발급된 접근 토큰은 만료까지 유효할 수 있습니다.
/owner-check.html은 시험 세션을 메모리에만 두고 정리 후 로그아웃합니다. 기존 메모는 시험하지 않습니다.
자동 점검은 공개 요청과 정적 코드·메타데이터 검사입니다. 실제 A·B 로그인과 DB authenticated 역할 직접 요청은 자동 점검에 포함하지 않습니다.
이전 공개 Git 커밋·배포·외부 캐시·내려받은 사본은 이번 작업으로 삭제되지 않습니다.
bundle-notes.json과 artifacts/submission.json은 커밋하지 않습니다.

# BYTE BACK 방어전 시작 틀 R5

이 저장소는 1단계에서 학생 본인이 GitHub 저장소와 Vercel 배포를 만드는 출발점입니다. 포함된 메모 네 건은 가상 자료입니다. 실제 학생 자료, 토큰, 비밀키를 넣지 마세요.

## 학생이 하는 일: 세 걸음

1. GitHub 계정을 만듭니다.
2. 방어전 1단계 카드의 **Deploy** 버튼을 누릅니다. Vercel에 GitHub로 로그인하고, 새 저장소가 **본인 계정의 Public 저장소**인지 확인한 뒤 Deploy를 누릅니다.
3. 배포가 끝나면 화면에 나온 `https://…vercel.app` 주소를 방어전 1단계 카드에 붙여넣고 제출합니다. 저장소 주소나 설정 파일은 적지 않습니다.

배포가 끝나면 `/`에서 점령된 가상 자료실을 볼 수 있습니다. `/data.json`에는 같은 가상 메모가 공개됩니다. 이 공개 상태를 확인하는 것이 1단계의 출발점입니다. 1단계 접수와 심판 판정은 포털에서 확인합니다.

## 시작 틀의 자동 처리

`vercel.json`은 정적 결과물 `public`을 배포합니다. 빌드 명령 `npm run build`는 Vercel이 제공하는 GitHub 저장소 소유자·이름, 커밋 SHA, 배포 URL을 검증하고 `public/aleph.json`을 생성합니다. 이 값이 없으면 빌드가 실패하므로, 성공한 것처럼 빈 주소를 내보내지 않습니다. `aleph.json`의 내용만으로 저장소 소유권이나 방어 성공을 인정하지 않습니다. 심판이 공개 저장소의 실제 커밋과 배포된 자료를 따로 대조해야 합니다.

`aleph.config.json`의 `repoUrl`과 `publicAppUrl`은 이전 제출 묶음 방식의 자리표시자입니다. 1단계에서는 학생이 편집하지 않습니다. 2단계 이후 코딩 도구가 필요한 설정과 보호 기능을 단계별로 작성합니다. `npm run bundle`과 `bundle-notes.json`도 1단계의 세 걸음에는 포함되지 않습니다.

로컬에서 가상 화면만 확인할 때는 `npm run build -- --local`을 사용합니다. 로컬 실행은 Vercel 배포나 심판 접수를 증명하지 않습니다. 저장소의 `src/attack-check.mjs`는 실제 배포가 된 뒤 `/data.json`을 비로그인으로 요청해 공개 가상 메모의 확인 표시를 읽습니다.

## 다음 단계의 코딩 도구에 전달할 규칙

[AGENTS.md](AGENTS.md)를 먼저 읽히고 한 번에 한 제작 단위만 요청하세요. 2단계부터는 자료 보호를 구현할 때 `public/data.json`을 복사하는 1단계 빌드 흐름도 함께 바꿔야 합니다. 3단계 이후의 로그인, 허용 경로, 5단계의 원본 API 주소, 6단계 이후 정책 규칙은 해당 단계 원고와 계약에 맞춰 추가합니다. 비밀번호·토큰·서버 전용 키·실제 학생 기록을 코드, Git, 제출 묶음에 넣지 않습니다.

`src/decider.mjs`와 `src/detect.mjs`의 로컬 시험은 반 엔진이나 운영 심판의 결과가 아닙니다. 1단계 이후 제출 묶음 계약 `aleph.defense.submission.v2`는 `scripts/bundle.mjs`에 남아 있으며, 코딩 도구가 해당 단계의 최신 배포 주소와 Git 원격을 맞춘 뒤 사용합니다.
